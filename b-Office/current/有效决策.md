# HistoryApollo 有效决策

这里只保留当前仍有效、会影响后续实施的决策。

## DEC-001 只做「一次调用」，不做会话

- 状态：已接受
- 日期：2026-09-07
- 背景：模型调用天然想往会话管理、提示词模板、重试编排上长。
- 决策：模块只把一次 chat/completions 调用说清楚。上下文由调用方持有并逐次回传。
- 原因：会话状态活在一个可热重载的模块里必然失真，反而让调用方以为自己不必管上下文。
- 后果：多轮对话由调用方拼 `messages` 数组；模块体积保持在几百行。
- 替代或废止条件：出现多个消费方重复实现同一套会话拼装，且形状已稳定时再议。

## DEC-002 密钥参数名必须以 token 结尾

- 状态：已接受
- 日期：2026-09-07
- 背景：宿主总线按**参数名**判定敏感值（`code`、`*token`、`*password`、`*secret` 等），
  `apikey` 不在其中。
- 决策：`apollo.key.set` 的密钥参数命名为 `token` 并置于位置 0，并由自动验证钉住。
- 原因：命名一旦改成更"自然"的 `apikey`，回显、命令历史和结果脱敏会同时静默失效——
  这类错误没有任何运行期症状。
- 后果：指令读起来略不自然；换来的是脱敏由宿主统一保证，模块不必自己实现一层。
- 替代或废止条件：宿主改为按描述符声明敏感参数时，改用那个声明。

## DEC-003 密钥落在运行包的 data/，不落在仓库或 vulcan.app.set

- 状态：已接受
- 日期：2026-09-07
- 背景：候选位置有三处：仓库、宿主通用配置（`vulcan.app.set`）、模块运行态目录。
- 决策：落在 `%AppData%\HistoryVulcan\Modules\HistoryApollo\data\providers.json`；
  同时支持环境变量覆盖，且环境变量优先。
- 原因：模块 API 合同保证升级时保留 `data/`，密钥不会被一次热装抹掉；宿主通用配置是
  全局键空间，模块的私有凭据不该占它。仓库则一律不放。
- 后果：换机需要重新提供密钥；`apollo.provider.list` 会报告密钥来源，便于分辨"改了库
  却仍被环境变量覆盖"这一类困惑。
- 替代或废止条件：宿主提供模块级凭据保管接口时迁过去。

## DEC-004 chat 指令不声明 Readonly

- 状态：已接受
- 日期：2026-09-07
- 背景：`Readonly` 表达"是否写入持久状态"，一次对话调用确实不写本机任何东西。
- 决策：仍然不声明 `Readonly`；只有 `apollo.model.list`、`apollo.provider.list` 是只读。
- 原因：这条指令会发出计费的外网请求。把它标成只读，等于告诉所有"只读即安全"的消费面
  可以随便调。
- 后果：只读白名单类消费面不会自动获得对话能力，需要显式放行。
- 替代或废止条件：宿主引入"有副作用但不写本机"的第三种声明时改用它。

## DEC-005 本仓不启用 Git LFS

- 状态：已接受
- 日期：2026-09-07
- 背景：体系内多个仓库因按扩展名批量套 LFS，出现指针失效与推送被拒。
- 决策：`.gitattributes` 只保留 `* text=auto`，Logo.png 作为普通二进制入库（281 KB）。
- 原因：新仓没有历史指针需要保活，不引入就没有失效面；单文件远未接近 100 MB 硬限。
- 后果：与体系内旧仓的 `.gitattributes` 不一致，这是有意的。
- 替代或废止条件：确有单个文件超过 100 MB 时，按精确路径逐个追加。

## DEC-006 项目合同检查自带规则，不转发到 Diana

- 状态：已接受
- 日期：2026-09-07
- 背景：模板的 `Test-ProjectContract.ps1` 转发到
  `2026-019-HistoryDiana/b-Code/OneHistory.ModuleContract.ps1`，该文件当前不在库中，
  转发会直接 exit 2。
- 决策：本仓自带一份只读规则，检查版本三处一致、模块身份、目录级别、失效链接，
  以及**密钥绝不入库**。
- 原因：一个永远失败的验收命令等于没有验收。
- 替代或废止条件：共享规则重新可用且覆盖上述检查时，改回转发。

## DEC-007 联网搜索由模块代模型执行（放宽 DEC-001 的范围）

- 状态：已接受
- 日期：2026-09-14
- 背景：DeepSeek API 不带搜索。首个消费方 HistoryMinerva 要按外购件规格查品牌，而且要「按需」——
  由模型自己决定何时搜、搜什么。这只能在一次调用内部跑工具循环，调用方在总线外做不到。
- 决策：`apollo.chat.*` 增加 `web=true`。模块在单次调用内执行 `web_search` 工具循环，搜索服务为博查，
  密钥进同一个 `ProviderStore`。循环有硬预算（5 次搜索 + 2 轮宽限），超出即失败回执。
- 原因：搜索服务的密钥、限流与错误翻译和模型调用是同一类问题，放在调用方会被每个消费方各写一遍；
  工具循环的状态只活在一次调用之内，不违背 DEC-001「不保存会话」的本意。
- 后果：一次调用可能是多轮 HTTP，`timeout` 按每轮计；费用是 token 加搜索次数两份。
  `web` 默认关闭，老调用方行为不变。
- 替代或废止条件：模型供应商原生提供可控的服务端搜索时，改为透传其开关并删除本地循环。

## DEC-008 调用过程按轮实时写进控制台，由本模块负责

- 状态：已接受
- 日期：2026-09-14
- 背景：HistoryMinerva 4.10.5 打包查品牌时，模型搜了什么、答了什么，要等整批查完才由 Minerva
  从结构化载荷里拼成一段打出来；查询进行中控制台上什么都看不到。而且这是 Apollo 的调用过程，
  放在消费方拼，每个消费方都得各写一遍，还跟着载荷字段名走。
- 决策：`apollo.chat.*` 把每一轮往返（提问、思考、要求搜索的词、每次搜索的结果标题、答复与用量、失败原因）
  一返回就写到 `CommandContext.Progress`，每段带进程内调用编号。消费方不再复述。
- 原因：进度通道是总线给每一条指令的，经总线的嵌套调用同样有，写进去就进控制台，消费方不用改；
  「把这一次调用的经过说清楚」本来就在 DEC-001 的范围之内。
- 后果：并发调用在控制台上交错，靠编号区分；思考与答复不截断，思考模式下输出较长。
  粒度是「轮」不是逐字：请求仍是 `stream=false`，回执形态不变。
- 替代或废止条件：宿主提供按调用分组折叠的控制台视图时，改为按组输出。

## DEC-009 0.3.1 工作区可直接构建

- 状态：已接受；日期：2026-09-28。来源：用户授权的体系架构清理。
- 决策：仓库根新增 `Directory.Build.props`，导入不入库的 `Directory.Build.user.props`，`.gitignore` 登记该文件。
  `vulcan.dev.start` 只在项目根有 `Directory.Build.props` 时才写本机覆盖点；此前 Apollo 在 F 盘工作区里构建或跑测试
  都要手动传 `-p:HistoryVulcanPackageRoot=`。与另外七个模块的布局一致。
- 后果：无代码与行为变化。

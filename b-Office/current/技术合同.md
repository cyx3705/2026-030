# HistoryApollo 技术合同

本文件是现行需求与系统架构的权威声明。与实现冲突时必须指出冲突，不得单方面改写。

## 现行需求

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| REQ-001 | 以 `apollo.chat.ask prompt=…` 完成一次单轮调用，回执正文即模型答复 | VERIFY-UNIT「result footer」「chat outcome」；VERIFY-ACCEPT |
| REQ-002 | 以 `apollo.chat.send messages=[…]` 传入完整消息数组完成多轮调用 | VERIFY-UNIT「transcript parse」 |
| REQ-003 | 支持 model / system / temperature / maxtokens / json / timeout / provider 七项可选参数 | VERIFY-UNIT「chat outcome」检查请求体 |
| REQ-004 | 密钥可由 `apollo.key.set` 写入本机，或由环境变量提供，环境变量优先 | VERIFY-UNIT「key roundtrip」「environment key wins」 |
| REQ-005 | 密钥在回执、日志、结构化载荷中只以掩码出现 | VERIFY-UNIT「mask」「secret parameter contract」；VERIFY-FULL 的入库扫描 |
| REQ-006 | 供应商的默认模型、接入点与默认供应商可配置并落盘 | VERIFY-UNIT「key roundtrip」 |
| REQ-007 | `apollo.model.list` 返回供应商当前可用模型 | VERIFY-UNIT「model list」 |
| REQ-008 | 输入错误与远端拒绝返回失败回执而不是异常堆栈 | VERIFY-UNIT「chat error mapping」「missing key」 |
| REQ-009 | 模块被热重载时释放连接池 | 代码审阅：HistoryApolloModule.Dispose；宿主在装新快照前调用 |

## 系统架构

```
宿主 CommandBus
   └─ ApolloCommandCatalog        指令声明：名称、参数、级别、脱敏契约
        ├─ ProviderStore          供应商档案与密钥（%AppData%\HistoryVulcan\Modules\HistoryApollo\data）
        ├─ ChatTranscript         参数 → 消息序列；结果 → 回执与结构化载荷
        └─ ChatClient             OpenAI 兼容 HTTP：/chat/completions 与 /models
```

- `HistoryApolloModule.Attach` 只做两件事：建 `ChatClient`、登记指令。不跨模块调用。
- `ModuleInfo.ModuleName` 显式返回 `HistoryApollo`，它同时是指令域 `apollo`。
- 模块只依赖冻结接入面 `IModuleContext.Bus` 与 `RegisterCommands`；不读设置、日志或数据根。

## 关键约定

### 密钥

- 落盘位置是运行包的 `data/`：按模块 API 合同，升级时宿主保留该目录，热装不会抹掉密钥。
- 解析顺序：`APOLLO_<供应商>_KEY` → `<供应商>_API_KEY` → 库文件。来源在回执里以 `keySource` 报告。
- 写密钥的参数名必须以 `token` 结尾且位置为 0。总线按参数名判定敏感值，改名成 `apikey`
  会让回显、命令历史与结果脱敏一起失效。该约定由自动验证钉住。

### 供应商

内置 `deepseek`（`https://api.deepseek.com`，默认模型 `deepseek-chat`）。新增一家只需在
`ProviderStore.Builtin` 加一行，或用 `apollo.provider.config` 在本机配一条——协议共用
OpenAI 兼容的 `chat/completions`。

### 返回

- 回执正文是模型答复本身，后接一行用量脚注；`json=true` 时不加脚注，整段回执可直接解析。
- 结构化载荷是 JSON 文本：provider、model、content、reasoning、finishReason、usage、elapsedMs。
- `deepseek-reasoner` 的思考过程在 `reasoning_content`，与正文分开返回，只进结构化载荷。

## 明确不做

- 不在模块内保存对话历史：一个会随热重载消失的会话缓存，只会让调用方以为自己不必管上下文。
- 不做流式输出：命令总线的回执是一次性的，流式需要另一套消费面。
- 不做自动重试：重试策略属于调用方，模块替它决定会掩盖计费与限流。

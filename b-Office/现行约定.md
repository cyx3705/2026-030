## 取舍

- **只做「一次调用」，不做会话。** 上下文由调用方持有并逐次回传；会随热重载消失的会话缓存只会让调用方以为不必管上下文。
  不做提示词工程、结果解析、业务自动重试（重试策略属于调用方，模块替它决定会掩盖计费与限流）。
  RATIO-NATIVE-002：本机请求按需加载定制 DLL；并发加载共用门闩，失败后自动加载冷却 30 秒，手动启动可立即重试。模块卸载取消加载和流。
- **联网搜索由模块代模型执行。** 搜不搜、搜什么由模型决定；`web` 默认关，打开后费用是 token 加按次计费的博查搜索两份。
  每次调用最多真搜 5 次，再宽限 2 轮仍只要工具就判卡住失败。单次搜索失败只告诉模型；博查没配密钥整次失败——那是配置问题，不该让模型装作查过。
- **调用过程归 Ratio 写进控制台。** 写 `CommandContext.Progress`，经总线的嵌套调用也有这条通道；消费方不要再从回执复述搜索与答复。
  粒度是「轮」不是逐字（`stream=false`）：控制台按行渲染，几路并发逐字刷屏反而读不清。
- **chat 指令不声明 Readonly。** 不写本机，但每次都是计费外网请求；标只读等于告诉「只读即安全」的消费面随便调。
- **密钥参数名必须叫 `token`、位置 0。** 总线按参数名判定敏感值，改成 `apikey` 会让回显、历史、结果脱敏同时静默失效（测试钉住）。
- **图片走识图供应商（0.5.0）。** 带 `images=` 且省略 `provider=` 时用识图供应商（内置 `qwen` 通义千问，`ratio.provider.use <名> vision=true` 可改），不用默认供应商。
  原因见下「真机才知道的」第一条。只收本机文件路径、不收网址（不替调用方多开出网口子）；超限直接拒、不偷偷缩图——缩到多小还看得清只有调用方知道。

- **本机推理服务归 Ratio，不再有单独的推理区（0.7.0，用户定）。** 源码在 `b-Code-Service/`，以嵌入资源随 DLL 发布，
  `ratio.local.start` 在服务没在跑时把它同步到运行区再启动——运行区只使用模块部署的定制 DLL 和配置，不在运行区改源码。
  运行区是 F 盘特例 `F:\ModuleServicesData\Ratio`（不进宿主 `ModuleData`）：KV 快照 40 GB 上限放不进 C 盘的模块数据区，原生 DLL 需要独立的快照空间；
  模型统一在 `F:\Models`。对话就是普通供应商 `local`（回环地址免密钥，不写默认模型——服务同一时间只装一个，调用时取它报出的那个）。
  换模给 Run（失败服务自己装回原模型），停服给 Ask（断所有客户端）。Sub2API 归 Juno 管；共享 KV、逐词概率及流式原语由下文 ratio.seq.* / ratio.local.probs 提供。

## 真机才知道的

- **DeepSeek 收图片但看不到**（2026-10-06 实测 `deepseek-flash` 返回空、`deepseek-v4-pro` 回答「无法查看图片」，都是 HTTP 200）。
  不报错的「看不到」比报错危险：模型会照着文字瞎编，所以带图请求必须换供应商，而不是靠服务端拒绝。
- 服务端会把 `deepseek-chat` 解析成当次主推模型（实调返回 `deepseek-v4-flash`），回执按服务端返回的名字报告；要固定模型就显式传 `model=`。
- DeepSeek 思考模式下带工具的后续请求必须把助手消息（含 `reasoning_content` 与 `tool_calls`）**原样**回放，自己挑字段重建就是 400。
- 博查在 HTTP 200 里也会返回业务错误（`code != 200`），按远端失败处理，不当「没有结果」。

## 推理原语（0.8.0）

给要逐 token 交互的消费方（Echo）用，替代它直连 11435 的私有 HTTP。只有供应商 `local` 有 `ratio.local.probs` 与 `ratio.seq.*`；`ratio.chat.stream` 任一 OpenAI 兼容供应商都行。Data 一律是 JSON 文本，字段只增不减：

- `ratio.local.probs` → `{"tokens":[{"token","logprob"}]}`（服务的 `/completion`，n_predict=1、temperature=0、cache_prompt）。
- `ratio.seq.caps` → 服务原样的能力对象（`supported`、`generation_streaming`、`backend`、`provider_parallel_slots`、`reason`…）；探测失败不报错，回 `supported=false` 与原因。
- `ratio.seq.open` → `{"sequence","epoch","prefixTokens"}`；`ratio.seq.choose` → 服务原样的一行结果（`label`、`decision_steps`、`shared_prefix_tokens`、`replayed_tokens`），旧服务没有 `select_text` 时自动拆成 prefix/tokenize/select 三步。
- 开流（`ratio.seq.stream`、`ratio.chat.stream`）→ `{"stream"}`；`ratio.stream.read` → `{"text","next","done","error"}`，`after` 传上次的 `next`（字符位置），读到 `done` 的那次后流即删除；闲置 90 秒的流自动取消，上游请求随之断开；同时最多 32 路。服务没有 `op=stream` 时退回逐步 `next`。
- 共享 KV 被服务拒绝时失败回执是 `shared_kv:<原因码>`（如 `shared_kv:invalid_sequence_size`），调用方按原因码决定是否退回普通对话。
- 模块卸载时把还开着的序列逐个释放。

### 整批分叉与续接（0.10.0，RATIO-KV-002）

起因是 Echo 伴读逐词选义慢（2026-11-11 实测端到端约 9.5 词/秒）。逐层量下来：服务里一次分叉约 50 ms，其中大半是固定开销——一次只算一个词、每次前向只有几十个 token，显卡远没吃满；宿主总线本身是进程内直调，不是瓶颈。所以改的是「一次算多少」，不是「调得多快」：

- `ratio.seq.batch sequence= epoch= jobs=[{"suffix","labels"}…] [prefix=]` → `{"results":[…与任务同序…],"serviceMs","batched"}`。服务（`op=select_batch`）把任务按「至多 `kv_branches` 条分叉序列、至多 `n_batch` 个 token」装组，每组所有后缀进同一次多序列前向。省略 `prefix` 表示在序列末尾分叉，不必每次重传整段前缀。旧服务没有这个操作时退回逐个 `select_text`（此时必须给 `prefix`）。
- `ratio.seq.append sequence= epoch= text=` → 同 `open` 的句柄字段。只算新增 token，此前的 KV 不动；失败时服务把整条序列清掉（循环状态回不去），调用方按 `shared_kv:stale_sequence` 重开。
- 实测（qwen3:8b，RTX 4080 Laptop）：整批后吞吐约 3700 token/秒，凑够 8 个任务（约 256 token）就到顶，再多只是排队；32 个任务与逐个 `select_text` 的标签 32/32 一致。**此后的上限是显卡算力，速度 ≈ 3700 ÷ 每词后缀 token 数**——要更快只能让调用方把每个任务的后缀写短。KV 精度（q8/f16）、日志级别对吞吐没有可测影响（试过，没改）。
- 模型配置（`config/echo-models.json`）新增可选键：`kv_branches`（分叉序列数，默认 1；每多一条只多一个序列号，但含循环状态的模型每条序列各占一份状态，所以只给 qwen3:8b 开到 32）、`batch` / `ubatch`（默认 256 / 128，即原值）、`kv_type`（默认 `q8_0`）、`verbosity`（默认 4）。
- 序列闲置回收从 90 秒放宽到 600 秒：续接要靠序列活着才省得下重算，闲着的序列只占 KV 格子。
- 服务二进制要手动重编（`scripts/echo-kv/build-native.ps1`）；`ratio.local.start` 只同步脚本、不编译。原生构建使用独立临时构建目录。

## 向量（0.9.0）

- `ratio.embed.texts texts=<JSON 字符串数组>` → Data `{"provider","model","dimensions","vectors":[[…]],"usage":{"totalTokens"},"elapsedMs"}`，向量按输入顺序；正文不放向量。
- 默认通义千问 `text-embedding-v4`（DeepSeek 没有向量接口，本机服务同一时间只装一个对话模型）；别家要写 `model=`。
- 通义的 `dimensions` 只认 64/128/256/512/768/1024/1536/2048 档（2026-11-08 实测，其他值 400），不在本模块校验——别家档位不同，交给服务端拒。
- 每批 10 条顺序发（通义硬限），任一批失败整次失败，不回半截。一次最多 500 条、每条 2000 字。
- 只做一次调用：不建索引、不存向量、不算相似度——语料与缓存失效规则归调用方（Diana 能力地图、Usus）。
- `ratio.chat.ask/send` 加了 `schema=`（json_schema strict）与 `think=false`（`chat_template_kwargs.enable_thinking=false`）。
- **代理丢唤醒（2026-11-11 修）。** `echo-proxy.cpp` 原先在锁外置 `finished` / `cancelled` 再通知，等待方刚查完条件还没睡下时通知就丢了，这次应答会一直挂到客户端超时（`select_text` 是 120 秒）。旧代理 2 万次空操作丢 15 次应答，修后 0 次（`linux-tmp/stress_proxy.py`）。这才是逐词调用「偶尔卡死」的根因；谓词读的标志一律在锁内改。

## Ratio 自有原生推理 DLL（RATIO-NATIVE-001）

- 本次定位：宿主 Core 源码 Release 空处理器基准（每档 20,000 次）中，约 1/8/32 KB 指令分别约 10.75/18.18/43.44 微秒，约 9.3/5.5/2.3 万次每秒；每次分配约 14.6/88.9/294 KB。这是纯总线微基准，不含模型、HTTP 或代理，不能当端到端吞吐。解析/JSON 与字符串分配是总线可优化项，但尚不足以解释逐词约 50 毫秒的服务开销。批处理仍有价值：它合并 GPU 前向和调度，Windows 原生 DLL 不会消除模型计算与排队。
- Windows 原生迁移消除本机推理路径的 HTTP、代理线程交接和 WSL 网络边界；不会承诺仅换系统即可大幅提高 token 吞吐。需同模型、同提示词、同批配置的前后实测才能给出加速倍数。已有约 3700 token/秒的数字属于 RATIO-KV-002 的历史实测，不是本次原生版测得。
- 用户选择直接在宿主进程内加载 Ratio 自有 `ratio-inference.dll`。唯一后端为 `native-dll`，移除后端环境开关、WSL 启停、代理和旧恢复实现。原生模式不开放 HTTP 监听；local 原地址仅用于路由身份，远端供应商与其他回环端口仍走原传输。
- 保留 RATIO-KV-002 的 `echo-kv.h`、`patch_server.py`、全部 `ratio.*` 参数和 JSON/SSE 回执。`patch_native.py` 只追加 C ABI、取消/生命周期入口和进程内请求分发；处理器仍投递原推理队列。模型配置的分叉数、batch/ubatch、KV 类型和模板沿用，不使用进程全局环境变量传分叉数。Echo 无需修改。
- 编译复用原来固定的 llama.cpp 提交与 SHA256；Windows 版本从同一源码编译 llama/ggml/CUDA，不使用 Linux .so。`buildNative` 只构建到临时目录，不安装、不启动模型。打包通过 `RatioNativeRoot` / `RATIO_NATIVE_ROOT` 嵌入生成的原生 DLL；`ServiceBundle` 在首次启动前解出，运行机无需编译工具。机器专用路径不进仓。
- 原生请求使用有界 SSE 缓冲，消费方关闭即取消；卸载先禁用恢复、关闭流和序列，再停止模型。引擎未停稳绝不释放 DLL 映射。原生错误会影响宿主进程，这是用户选择进程内 DLL 的边界。
- 换模先封新请求，仍允许释放旧租约；等公共槽和 A/B 空闲、保存公共槽后才换。失败装回旧模型。原生快照独立存放 `native/slots`，以 DLL 摘要、模型和槽命名，不读写 Linux 现有 KV 快照；保存失败保留运行模型，40 GB 预算超限拒绝保存。
- 验收：`commands.test` 覆盖原生命名路由、单模型启动、保留批配置、换模回退、快照失败保活、停服期间释放租约与流取消；`commands.testNative` 对固定上游应用原补丁及新补丁，逐字节核对 KV 源码，编译运行真实 C ABI 的无模型夹具。Windows GPU DLL、真模型与性能验证单独记录，不能用假引擎或 Linux 兼容编译代替。
- 2026-11-11 已验证：45 组离线测试；固定上游 C ABI 夹具（含加载途中停机）；Windows MSVC CPU DLL 真实 qwen3:8b 的批处理/逐个标签一致、append、流式输出和零租约；Qwen2.5 0.5B 的双槽快照保存/恢复与同 DLL 重启。0.5B 模型 SHA256 使用官方 LFS oid 核对，不把 Xet ETag 当文件 SHA256。CUDA Toolkit 12.8 与 MSVC x64 已安装，未更换驱动；小模型功能验收未停生产 WSL 服务，后续 8B 对照按用户授权临时停服后恢复，未热装候选。
- Windows GPU 实测：MSVC 19.44 / CUDA 12.8.93 / CMake 4.4.4，目标 SM 89，RTX 4080 Laptop，Qwen2.5 0.5B Q4_K_M 的 25/25 层 GPU 卸载；3 项同批选义服务时间样例 9.6 ms，批处理加 3 次逐个调用共 40.8 ms。通过标签逐项一致、append、8-token 流、零租约、双槽快照、同 DLL 重启，以及真实管理层启动/换模/停机/重载恢复。这是独立小模型功能验收，不能与历史 8B 性能相除推断提速；8B 对照见下一段。
- 候选构建已生成包含 CUDA 与 MSVC/OpenMP 可再发行运行库的 Ratio.dll（约 825 MiB），所有依赖随候选携带；大型嵌入资源会增加宿主热装的磁盘和内存开销。先前功能验收在隔离测试进程完成；后续宿主安装与生产切换见 RATIO-NATIVE-002。

### 同模型选义速度对照（2026-11-11）

用户明确授权临时停旧服务、测完恢复；未热装候选。qwen3:8b 使用同一 GGUF，32768 context、2 公共槽、32 分叉、2048/1024 batch/ubatch，RTX 4080 Laptop；固定原 RATIO-KV-002 的 32 项任务，摘要 `83F5E53105525A1C5C6566E9ECA3052A185507B123948A93CA6F609791534D9C`。每阶段 1 次预热、5 次计时，依次旧 WSL+代理 → 原生 DLL → 恢复旧服务再测；模型加载时间不计入，前缀预填另列。

| 中位数 | 旧后端（前测） | 原生 DLL | 旧后端（恢复后复测） |
| --- | ---: | ---: | ---: |
| 选义本体，词/秒 | 39.78 | 43.75 | 40.10 |
| 含前缀预填，词/秒 | 36.29 | 39.92 | 36.51 |
| 32 项选义耗时，毫秒 | 804.35 | 731.50 | 797.99 |

将两次旧后端共 10 轮合并取中位数：选义本体 40.04 → 43.75 词/秒（+9.26%）；含预填 36.42 → 39.92 词/秒（+9.59%）。32/32 标签在两个后端、各轮完全一致，结束均为零租约。用户所述约 35 词/秒接近本次含预填旧基线，但历史页面样例不是同一工作量，不用 35 直接计算加速倍数。本次测 Ratio 推理链路，不含浏览器 DOM、词典查询、整页排队和全部正文长度；不能把约 40 词/秒当成任意网页的保证。结果反映 Windows/MSVC/CUDA 与去掉旧传输链路的整体变化，不把全部增益归因于总线或 HTTP。该次对照结束时曾恢复旧服务；后续已永久迁移到定制 DLL，见 RATIO-NATIVE-002。
